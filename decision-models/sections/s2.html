At temperature 0 the text interface always takes the most likely word (greedy decoding). Above 0 it draws a word at random, weighted by the odds, so the less likely word comes out some of the time.

the whole mechanism in four lines
  1. Prefill: the model reads the entire conversation in one pass. Attention lets every position look at the others; the result is a KV cache and a hidden state at every position. Almost all of the cost lives here when the answer is one token.
  2. Scoring: the final layer emits logits for every token in the vocabulary, and softmax turns them into a spread summing to 1. At the answer position the spread has P(Yes) = 0.562 and P(No) = 0.438. The model has already decided how sure it is. That number exists whether or not anyone reads it.
  3. Decode: the API draws one token from the spread, shaped by temperature, and emits it as text. The draw is a coin weighted by the spread, and 0.562 is a coin that lands both ways. The text is a sample from the spread, not the spread.
  4. The readout: the API returns the logprob of each top candidate alongside the sample. Read it, and 0.562 comes back with the answer. That is all the technique is: a field you were allowed to have.
where the time goes (measured on our 27B, one request at a time)

Prefill reads every prompt token; decode adds one step per output token. For a one-token answer the bill is almost all prefill, and prefill grows faster than the prompt does:

Three readings. Decode is cheap here: generating the letter plus an end token instead of reading the logprob cost about 50 ms on a short prompt (147 vs 99 ms on 400 benchmark items) and 20 to 50 ms on long ones. Long context is expensive the first time: cold throughput falls from about 7,000 tokens/s at 9k tokens to about 3,800 at 116k, because full attention is quadratic in length. Reuse is the lever: the server keeps the prefill of a prompt prefix (prefix caching), so a second question about the same 116k-token transcript costs about 1 s instead of 30 s, if the transcript comes first, stays byte-identical, and the question comes last.

A catch specific to our model: it is a hybrid, where 48 of its 64 layers are recurrent (a fixed-size state instead of a growing KV cache) and only 16 use full attention. vLLM can only cache that recurrent state in whole blocks of 1,584 tokens, and in our runs the hit was always one block short. Prompts under about 3,200 tokens never hit the cache at all, which is why the first two rows have no warm speed-up. The same state costs about 148 MiB per running request whatever its length, so for short decisions it is the state, not the prompt, that caps how many run at once.

where the confidence number comes from (it is the weights, nothing else)

The 0.562 is not an extra certainty dial the model rates itself with. It is computed, in one final matrix multiply, from the model's learned output weights: the hidden state at the answer position is multiplied by a learned matrix that has one row per token in the vocabulary, and the row for "Yes" comes out 0.562 after normalization, the row for "No" 0.438. The weights that learned how to continue this text are the same weights you are reading when you read the probability. There is no separate confidence module.

Two things it is not. Not quantization: FP8 or INT8, the compressed storage the model is served in, is how the weights are held in memory, not what produces the number; an FP8 build usually moves the spread only a little, but on a borderline row a little can cross a threshold, so re-measure whenever the checkpoint changes. (The numbers on this page come from the model we serve, Qwen3.8-27B-Uncensored-FP8: an uncensored fine-tune, which is known to shift output distributions. Treat every probability here as a fact about that variant.) Not a weight you can tune: the only knob that touches the spread is temperature, and it applies at sampling time, after the number exists. The reason the number is usable as confidence at all is that the output weights were trained by next-token prediction over trillions of tokens, so they put high scores on correct continuations; the size of the scores is a byproduct of that training, which is exactly why a base model can be confident and wrong (section 4 measures the gap).
